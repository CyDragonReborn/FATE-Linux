AUM Console Introduction

AUM, the Application Update Manager, is a (2005) version of a project to mostly automatically patch our games. It contains feature to handle making the patch.exe proper, the metadata that is used to describe the patch, and the server component to actually make the patch availible. The overall project also includes doucmentation and a sample program that uses many of the AUM features.

The AUM Console (AUM_Console.exe) is a command-line program that can either interactively or non-interacticly handle many of the tasks that AUM needs. In particular, it can

  • Compare directories and make a list of added/changed/deleted/same files
  • Convert that list into an NSIS installation script
  • Run NSIS on that script, generating the Patch.exe that will upgrade a user
  • Make a simple patch manifest with a description of the patch
  • Add language-specific information to the patch description
  • Add extra game-specific information (e.g.: some games might have an audio description of a patch)
  • Update the patch manifest when the patch.exe or extra data changes

Run AUM_Console.exe from any Command prompt to start. A question mark will, at most prompts, give you some information. Type exit to quit.

Deploy to the Server

AUM_Console does not have any commands to deploy to server. In general, all that a patch needs to be deployed is for the static files patch.exe and patchmanifest.xml be added to the server; my basic scheme is to place files in http://server/updates/programname/updates/download so that they match their location on the end-users machine.

However, there is one step that must be done: the patch manifest must be updated to include technical details about the patch.exe (in particular, the patch.exe's CRC and SIZE). This is done with the update patchmanifest command. Note that you must first have a patch manifest loaded ( read patchmanifest or make patchmanifest) and the patch exe must be known (set patchexefile or make nsis).

If you use the scripting capabilities of AUM_Console, it might make sense to put your standard copy command into the script file using the run external or run dos command.

AUM Console Reference Manual

Internationalization

Some of the strings and data in the patch manifest file are internationalized. This means that each value (for example, the 'about short' value) is a series of language/value pairs. The language should be in 'setlocale' format (example: "English_United States"). When your game runs, and it needs an internationalized string, the AUM code will

  • Find out the current locale (using setlocale(LC_ALL, 0)). For example, setlocale might return "English_United States.1252".
  • Break that string into sections (English + United States + 1252)
  • Look through all of the language/value pairs and try to find the best match. The best match will have the most number of sections which match: "English_United States" matches more closely than "English_Canada" because two sections match.
  • If there are several possible matches (e.g., you only have English_UK and English_Canada and the locale is English_United States) then the first match will be selected.
  • A minor exception is that a language with a star (*) in will take priority over a language without a star. This means that if you want a default English, you should use "English_*". Similarly, you should use "*" as the language name to make the global bakup string to display when nothing else matches

The extension mechanism is internationalized, too. Each extension item can also have a language. Note that the languages can be different than the about short (and in turn, that can be different than the about long).

Some extension items are '_autowrite' values. It's important to know that both the name of the autowrite file and the actual data are versioned. Not only that, but if, when the patchmanifest.xml is downloaded, the game is one locale, and later you switch to a different locale, the file on disk is not updated.

To add non-ASCII characters to the aboutshort, etc values, use this syntax: "This is a U+0F20 Tibetan character". Values that understand this syntax are the add commands.

add patchmanifestextension

The patch manifest includes an extension mechanism so that you can add data specific to your game in the patch. The data might be workflow data to help the patch process; it might be rich media to be displayed with an update. Whatever it is, it contains a name (like "author" or "created on" or "videoclip"), a language (in the same format as the aboutlong and aboutshort) and a value (like "Peter", "5-DEC-2005", or a BASE-64 string).

Work flow for add patchmanifestextension:
Previous command: add patchmanifestaboutshort
Next command: run updatepatchmanifest

The AUM_Console does not currently enforce any particular scheme for extension data except that names that include "_auto" may be treated specially either by AUM_Console or data by the game. If WildTangent marketing decides that certain must always be provided with a patch, then part of the work in implementing such a decision should include updating AUM_Console to enforce those requirements.

All *_autoread extensions will be expanded out with the run updatepatchmanifest command. The value in the *_autoread extensions is assumed to be a filename; that file will be read in and converted into a BASE64 string. That string will then be added in as an extension with the name "*".

Some technical details: the * is, of course, to be read as "any string" -- for example, "videofile" would be turned into an auto-read extension by calling it "videofile_autoread". Secondly, since extensions are internationalized, it stands to reason that the _autoread variable won't just be looked up; instead each of the languages that make up the _autoread extension will be looked up and each of the files will be found. Thus, if there's a sound_autorun and it has three languages, then after the run updatepatchmanifest is run the sound extension will also consist of three languages. Lastly, the run updatepatchmanifest command will first delete all of the autorun variables -- so if you first set sound_autoread with one language, and run updatepatchmanifest, and then change the language to something else and run updatepatchmanifest, your original setting and the addition to the sound extension will be lost.

All *_autowrite variables will be handled on the end-users systems. Each *_autowrite variable will be converted from BASE64 back into a regular file; the name of the file is the one mentioned in the *_autowrite extension. Note that only one file will be written out: if you have an extension with multiple languages (e.g., "videofile") you can add a single videofile_autowrite with a single language (use '*') and a single value ("videofile.avi") and the one file prefered by the user will be written out. The file is written out when the patchmanifest.xml file is downloaded (when the state machine is in state 1 'amdownloadingmanifest').

optionmeaning
namename of the extension to add
languageThe language that the extension is in; must be in Language_Country.CodePage format like the format used by 'setlocale'
valueNew value to add. With a little luck, these will actually work in multi-byte languages, etc.

Don't forget to run write patchmanifest after this command!

read commands

The read commands command will read in an external file full of AUM_Console commands and read them. Note that AUM_Console is not like some programs which silently interchange between interactive mode and file mode: you must specify a complete command in each line of the text file. If you fail to specify all of the arguments for a command, AUM_Console will prompt for the remaining arguments even if they are really just on the next line.

There are two special features of the command file that will help you write good batch files.

Firstly, @ will cause the line to not be echoed. This is just like Microsoft's DOS environment.

Secondly, the backslash (\) character lets you run a command over multiple lines. In particular, whenever the read commands command reads in a file, and a line end with a backslash, the backslash is removed and the next line appended on except that all whitespace at the start of the next line (spaces and tabs only are whitespace) are ignored. This lets you make nicely indented command lines. Note that strings will automatically flow over the end of line (see the make patchmanifest example for a sample of strings running over lines.

The run checkconnection command calls the WTPlatform 'WTPlatform::System::Net::CInfo::IsConnected' method and prints out the return value. This command is intended more for the QA group than as part of the work flow for AUM.

The run dos and run external commands will run an external program by spawning a new process and waiting for it to complete. The difference between them is that the "run external" command needs an actual program to run (like "notepad.exe") but the "run dos" command automatically runs the DOS shell (cmd.exe)(with the /C switch).

  2. If you need to just run the nsis program, you can run the set nsisfile command.



run prune

The run prune command takes the masterdirectory (from a read masterdirectory or make masterdirectory command and strips out the pieces that are not appropriate for a patch. As of 2-DEC-2005, this is all of the subdirectories underneath the "updates" directory

Work flow for run prune:
Previous command: make originaldirectory
Next command: make nsis

run tests

The run tests command runs some internal tests. If the tests fail, AUM_Console will abort() with a nasty message. The exact nature of the tests varies considerably from one build to the next.

run updatepatchmanifest

The run updatepatchmanifest command will update the patchmanifest object in two ways: firstly, the patch.exe CRC and size will be filled in, and secondly the patch extensions (set in add patchmanifestextension) with _autoread are filled in.

Work flow for run updatepatchmanifest:
Previous command: add patchmanifestextension
Next command: write patchmanifest

You should always run updatepatchmanifest before you deploy the patch manifest. Otherwise the values for patch.exe CRC and size and the _autoread values might be incorrect.

However, for the update to work the AUM_Console must know where the generated patch.exe is. This is either set automatically when you make the patch.exe (using the make nsis command) or you can use the set patchexefile command. In addition, the actual value is stored in the patchmanifest so if the value has been previously set in a patchmanifest, and the patchmanifest was written to a file (which it usually is), and if you've read the patchmanifest back in (which you usually will), then the value should be set already.

You can examine the current value with the dump patchmanifest command.


set

The set command lets you set the value of different variables that are normally set by one command and then used by another command. The philosophy of AUM_Console is that each basic command must both have a good "flow" (which means saving information from one command to the next so that no information needs to be entered twice) and must be partitionable so that each step can be done by different people on different days.

set commands are:

  • set DFV (designed-for-version value)
  • set height (height of screen)
  • set nsisfile (file to use in run nsis)
  • set patchexefile (file to use in run updatepatchmanifest)

You can see what all of these value are with the dump command. For example, dump DFV will show you what you set the set DFV command.

set DFV

Sets the 'designed for version' value. All scripts must have, as their first real line, a set DFV value so that we can change the AUM_Console as our needs grow. AUM_Console starts off with the DFV set to 1; however you cannot set the value to anything less than 2. In addition, it cannot be set to a value greater than the current AUM_Console version number.

See also dump DFV and dump version to find out the current DFV value.

set height

Sets the height of the console screen in lines. This is most useful when creating screenshots. Note that you cannot make the screen infinitely large -- this just calls into the SetConsoleWindowInfo Platform SDK function and hopes for the best. (see write printscreen).


set nsisfile

The nsisfile value is used by run nsis to find the .nsi file that the nsis command needs to generate a patch.exe file. The value is automatically set with the make nsis command.

set patchexefile

The patchexefile value is used by run updatepatchmanifest to find the patch.exe file; that exact file will have its CRC and file size calculated and placed into the patch manifest. The value is automatically set with the make nsis command.

Unlike the nsisfile value, the patchexefile value is actually stored in the patchmanifest.xml file; this means it is also automatically set when you read in a patchmanifest whose patchexefile has been set.


write

The write commands in general create an output file containing some information. You can write each of the XML AUM objects that AUM_Console can make (write masterupdate, and write patchmanifest), plus the masterdirectory intermediate object. In addition, there are some useful other write commands.

write commands are:

  • write cls
  • write masterdirectory
  • write masterupdate
  • write patchmanifest
  • write patchmanifestautowrite
  • write printscreen

write cls

The write cls command attempts to clear the screen. It does so by simple writing a series of '\n' (new lines) to the screen; for most purposes this is good enough.

Note to QA: unless this not-quite-right behaviour actually interferes with some other objective, bugs will not be entertained on this subject.

write masterdirectory

write masterupdate

write patchmanifest

All of these write commands simply write the existing objects out to a file specified by an 'ofile' parameter. In the case of masterupdate it's not really needed: the make masterupdate command will make the object and write it into a file for you and there are no commands to modify an existing masterupdate. In the case of masterdirectory and patchmanifest, however, there are commands to modify the object at which point you will probably want to write out the object.

Work flow for write patchmanifest:
Previous command: run updatepatchmanifest
Next command: none; this is the last command in making a patchmanifest.

optionmeaning
ofilefile to write to



write patchmanifestautowrite

The write patchmanifestautowrite command will write all of the "_autowrite" extensions out to a directory. This mimics what the game will do when the patchmanifest is downloaded and lets you have more confidence that the files embedded in the patch manifest are correct.

See also add patchmanifestextension for more details.

optionmeaning
odirdirectory to place autowrite files in


write printscreen

The write printscreen command is used primarily to make this documentation. It makes a very inefficient BMP bitmap file which is a screen dump of just the command windows that the AUM_Console is running in.

optionmeaning
ofileoutput .BMP file

!SD!

The very special !SD! command does a screen dump. This has not been tested and should be considered a candidate for removal. Note to QA: unless this command causes actual issues, bugs will not be entertained on this issue.
